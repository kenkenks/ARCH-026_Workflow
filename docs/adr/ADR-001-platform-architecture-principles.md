# ADR-001: 汎用アプリケーション開発基盤の設計原則

- 日付: 2026-11-05（JST）
- 状態: 採用（方針のみ。具体契約・実装は未決定）
- 対象工程: Phase 5B 設計方針の記録
- 関連計画: [最小契約設計計画](../plans/PHASE-5B-minimal-contract-design.md)
- 番号確認: 作成時点のリポジトリ内に既存ADR番号体系・ADR-001との衝突は確認されなかった。

## 背景と解決したい問題

ARCH-026にはワークフローの設計骨格、実行プロトタイプ、GUI検証資産がある。一方、これらの契約は未統合であり、汎用アプリケーション基盤としての環境移植性はまだ検証されていない。

既存資産の調査では、純粋な変換・検証処理や依存注入の接続点がある一方、DB、実行環境、通信、認証、業務構成の依存が複数箇所に残ることが分かった。既存システム全体の汎用化を待つことも、既存資産を無条件に移植することも避け、必要な境界から検証する。

## 中心設計原則

**依存層を差し替えるだけで、アプリケーションCoreを変更せずに、異なるDB・実行環境へ移行できること。**

これを基盤全体の最上位の設計判断基準とする。対象はDBだけでなく、ブラウザ、通信、認証、サーバー、ビルド、デプロイを含む。

環境固有の機能はCapabilityとして明示する。環境名による分岐や環境SDKへの依存を共通Coreへ混入させない。Capabilityの表現、要求と提供の照合、非対応時の扱いは次工程で設計する。

## 正式な要件

1. DB・実行環境の変更に対し、依存層以外の変更を不要にする。
2. Schema機能でテーブル・コレクション構造を追加・変更・削除できる。
3. 環境固有の特化オプションを選択できる。
4. Build・Deploy・Migrate・Syncなどのコマンド体系を統一する。
5. 新規アプリケーションを生成できる。
6. CJob・WorkflowなどのCore構造・機能を管理できる。
7. HelloWorldを標準検証アプリとして用意する。

これらは目標要件であり、現時点で実装済み・検証済みであることを意味しない。

## 採用するアーキテクチャ方針

- アプリケーションCoreは環境非依存の契約に依存し、環境固有のI/OはProvider / Adapter側に置く。
- ブラウザ・通信・認証・サーバー・DBの境界を設計対象に含め、DBだけの交換をもって移植性達成とはしない。
- Schemaの論理構造と保存先への投影を区別し、Schema VersionとMigrationを初期契約設計から考慮する。
- Capabilityは環境固有機能の明示と選択に使う。全環境がすべての機能を提供するとは仮定しない。
- 統一コマンドは名前だけでなく、入力、成果物、副作用、失敗時の扱いを整理する。
- 必要性を確認してから抽象を追加する。既存Repository等との重複や並行した業務APIを無条件に増やさない。

Provider / Adapterの厳密な区分、登録方式、型、メソッド、エラー形式、構成ファイル形式は本ADRでは定めない。

## 既存資産の抽出方針

既存システム全体を汎用化してから抽出する方式は採用しない。

- 純粋な汎用処理は必要に応じて抽出する。
- 業務依存が残る部分は、既存システム側で必要最小限の境界整理を行ってから抽出する。
- 統一CLI、アプリ生成、汎用Schema Migration等はARCH側で設計する。
- 既存システムへの再適用は、汎用基盤の契約と動作を検証してから行う。

現段階では既存システムを読み取り専用とする。境界整理の実施は今回の承認範囲に含めない。ソースの公開・再配布可能範囲、依存関係、合成データによる検証可能性を抽出前に確認する。

## HelloWorldの役割

HelloWorldは文字表示デモではなく、環境移植性を検証する最小アプリケーションとする。

- Read: 既存データの取得。
- Write: 既存データの更新。
- Add: 新規データの追加。

Add後のRead、Write後のRead、不正データ・競合の扱い、永続化先の切替時にCoreを変更しないことを確認する。さらにブラウザ・通信・サーバー・DBを通した動作を確認する。

| 段階 | 対象 | 到達点 |
| --- | --- | --- |
| HelloWorld-A | Repository契約とMemory / Local file等のAdapter | Repository境界、保存先交換、永続性の検証 |
| HelloWorld-B | ブラウザ・通信・サーバー・DB | 最初のエンドツーエンド環境移植性検証の成立 |

Memoryだけで永続性を保証しない。具体的な環境の組合せ、競合条件、操作の詳細な意味、受入手順は次工程で決める。

## CJob・Workflowの位置づけ

CJob・Workflowは、現時点では独立したオプションモジュールとして扱う。すべてのアプリケーションやHelloWorldの必須依存にはしない。

既存の「ワークフローは業務を知らない」という原則は維持する。既存Core、prototype、GUI Runtimeの統合方法や実行契約を本ADRで確定しない。

## 採用理由

小さな検証アプリを共通の基準にすることで、依存層の交換が実際にCoreの変更なしで成立するかを評価できる。既存資産の有用な処理を活用しながら、業務全体の整理や不要な抽象化を先行させずに済む。MigrationとCapabilityを初期から検討し、後付けによる契約破壊のリスクを減らす。

## 制約・リスク

- 本工程は文書作成のみ。コード、テスト、設定、Schema、既存文書は変更しない。
- 実装、Build、Deploy、Commit、Push、外部公開は行わない。
- 公開資料には業務データ、個人情報、秘密情報、内部環境情報を含めない。
- 保存先の型・主キー・競合・トランザクション能力の差を、共通契約でどこまで扱うかは未検証。
- ブラウザ側やBuild側に環境分岐が残ると、DB Portだけでは移植性を満たせない。
- Schema削除や型変更はデータ損失を伴い得る。定義の変更と実データへの適用を区別して設計する。
- Mockだけの成功を実環境での動作保証としない。
