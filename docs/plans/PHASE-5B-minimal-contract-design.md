# Phase 5B: 最小契約設計の作業計画

- 日付: 2026-11-05（JST）
- 状態: 計画記録。最小契約の具体設計・実装は次の指示待ち。
- 判断基準: [ADR-001](../adr/ADR-001-platform-architecture-principles.md)

## 目的と今回の境界

依存層の交換だけでアプリケーションCoreを変更せずに移植できる基盤に向け、次工程で設計すべき責務と確認事項を整理する。

本書は作業計画であり、型定義、APIシグネチャ、構成形式、エラーコード、Migrationアルゴリズム、利用製品を確定しない。以下の作業は次の指示を受けて着手する。今回は本書とADRのみを作成し、実装・Build・Deploy・Commit・Pushは行わない。既存システムは読み取り専用とする。

## 設計対象と成果物の計画

以下の「入力・出力」は設計で整理する情報の範囲であり、確定APIではない。各対象の成果は契約候補、根拠、代替案、検証計画、残課題を持つ設計資料とする。

| 対象 | 責務として整理する事項 | 入力・出力として検討する事項 | 依存方向 | 検証方法の計画 | 設計完了条件 |
| --- | --- | --- | --- | --- | --- |
| Application Definition | アプリの構成、利用モジュール、Schema・Provider・Capabilityの関連を表す範囲 | 論理アプリ定義と環境構成の区分、構成検証結果。秘密値の受渡し境界 | 構成側がCoreとAdapterを組み立てる。Coreは環境構成を参照しない | 同じCoreを複数構成へ割り当て、不正な組合せを列挙する | 論理定義と環境設定の境界、識別・参照・検証の責任が説明できる |
| Schema・Schema Version | 論理構造、型、必須、主キー、version、保存先投影と変更管理の分離 | 論理Schema、対象version、変更要求と、検証・差分・移行計画の関係 | Coreは論理契約に依存。物理構造への変換・適用は依存層 | 追加・変更・削除・型変更・既存データありの例を比較する | version互換性とMigration境界を整理し、後付けで契約を破壊する未整理箇所が明示される |
| Repository Port | Read / Write / Add、データ所有、未存在・競合・不正値・非同期の扱い | 論理ID・レコード・必要な更新条件と、取得値・書込結果・失敗情報 | CoreがPortを利用しAdapterが実装する。SDKや物理名はPortへ露出させない | 共通契約テストのケースをMemory / Local file等に適用する計画を作る | 操作ごとの意味、ID責任、データ型、競合、エラー境界が曖昧でない |
| Provider / Adapter | 選択・組立て・初期化・終了、保存先とHostの区分 | 構成・注入依存・Capability要求と、利用可能な実装・初期化失敗 | 具体実装がCore側の契約へ依存。構成入口で選択 | Adapter交換時に変更してよい箇所と禁止する箇所を比較する | ProviderとAdapterの用語・責任、対応組合せ、依存閉包が整理される |
| Capability | 環境固有能力の要求・提供・選択・非対応の扱い | 要求能力・提供能力・特化オプションと、適合結果 | 能力の契約と環境固有実装を分離し、Coreで環境名分岐をしない | 能力不足・任意能力なし・矛盾する選択の例を検討する | 必須／任意、非対応時の扱いと、Coreに依存を漏らさない規則が整理される |
| Browser Communication Port | ブラウザからの呼出し、通信エラー、認証・認可境界、再送の責任 | 論理操作・入力・認証文脈と、結果・失敗・再送条件 | UI側のアプリ処理は通信契約を利用。fetch・SDK・Host固有形式はAdapterへ置く | サーバー経由の正常・不正・未認証・権限不足・通信断・重複送信を計画する | ブラウザ、通信、認証、サーバー各境界とAdd再送時の重複防止責任が整理される |
| HelloWorld-A | Repository境界と保存先交換の最小検証 | 合成Schema・操作シナリオ・構成と、契約適合結果 | 同じCoreからPortを経由しMemory / Local file等を交換 | Add→Read、Write→Read、不正値、競合、未存在、永続化を確認する計画 | Core無変更の比較方法、Memoryの限界、再起動確認を含む受入基準が定まる |
| HelloWorld-B | ブラウザ・通信・サーバー・DBを通す移植性検証 | Aの契約、UI操作、環境構成と、E2E比較結果 | アプリケーションCoreを維持し、各境界の依存層を交換 | 複数の対応構成で同じシナリオを実施し、Core差分と結果を比較する計画 | 比較する環境・交換範囲・E2E手順が決まり、最初の環境移植性到達点を判定できる |

## Schema Migrationを初期設計に含める

Schemaの追加・変更・削除を、単なる定義ファイル編集として完結させない。少なくとも次を初期検討に含める。

- Schema Versionとアプリ・保存済みデータ・Adapterの対応関係。
- 変更差分、互換／非互換、物理構造の変更とレコード変換の区分。
- 適用前確認、計画と適用の分離、適用状態・履歴、再適用時の扱い。
- 削除・型変更・途中失敗・競合・中断後再開・復旧の責任と制約。
- 保存先により適用不要な構造変更や、提供できない能力の表現。
- 古いアプリと新しいSchemaの共存可否、Repository契約への影響。

初回HelloWorldで全Migrationを実装するとは決めない。将来の追加に必要な境界を検討し、初回対象と延期事項を理由付きで示す。ロールバック可能性や全DB共通の原子性は仮定しない。

## 横断して整理する事項

### 統一CLIとアプリ生成

Build・Deploy・Migrate・Syncについて、入力、出力、変更対象、副作用、実行計画・適用の区別、終了結果を整理する。Syncの対象を明確にし、データ同期・Schema差分・文書生成を混同しない。dry-runの語だけで書込なしと仮定しない。

アプリ生成はApplication Definition、最小Schema、HelloWorld、構成、検証資産のどこまでを生成するか検討する。既存業務の環境設定やデータをテンプレートへ含めない。CLIや生成器の具体実装は別工程とする。

### CJob・Workflow

独立したオプションモジュールとして、HelloWorldの必須依存から外す。既存Core・prototype・GUIの契約差を参照し、将来の統合・version・公開API管理を検討対象として残す。CHECK、WAIT、Ticket、イベント、停止・再開等の既存未決定事項を本計画で解決済みにしない。

### 既存資産と検証

過去調査を利用し、候補を純粋処理、境界整理が必要な処理、ARCHで設計する処理、業務固有処理に分ける。抽出候補は依存ファイル、利用権限・公開範囲、必要な整理、テスト根拠を確認する。既存システムの変更は別途指示があるまで行わない。

検証は契約テスト、Adapter検証、E2Eを区別する。Mockと実装の共通契約を確認し、Mockの成功だけで実サービスや障害時動作を保証しない。すべて合成データを使用する。

## 次工程の推奨順序

1. 既存文書との適用範囲を確認し、用語、対象、未決定事項を揃える。
2. HelloWorld-A/Bの操作シナリオと移植性の判定方法を設計する。
3. Application Definition、Schema Version、Repository Portを相互に検討する。Migration境界も同時に確認する。
4. Provider / Adapter、Capability、Browser Communication Portを設計し、A/Bのシナリオで依存の漏れを確認する。
5. CLI・生成・オプションCoreとの接続点を整理し、最小範囲と延期事項をまとめる。
6. 契約候補・代替案・リスク・検証計画を提示し、実装へ進む判断を待つ。

この順序は計画であり、現時点で作業開始や実装を承認するものではない。

## 次工程の設計完了条件

- 表の各対象に責務、入力・出力、依存方向、検証方法、完了条件が具体化されている。
- 同じCoreを維持して交換する依存層と、対応しない組合せが説明できる。
- Schema変更・削除とMigrationを考慮した契約になっている。
- HelloWorld-AはRepository検証、Bは最初のE2E移植性検証として区別されている。
- 未決定事項、延期事項、既存契約との差、公開上の制約が明示されている。
- 実装前に設計結果を提示し、次の指示を待つ。
